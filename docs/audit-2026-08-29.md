## 3. 表示ロジック

### lib/otcClass.ts の中身（区分ごとの表示文字列を全部）

`lib/data.ts` にあるのではなく `lib/otcClass.ts` 単体ファイル。全文は以下（`lib/otcClass.ts:10-15`）:

```ts
const OTC_CLASS_INFO: Record<OtcClass, OtcClassInfo> = {
  class1: { en: "Class 1 medicine", ja: "第1類医薬品", isClass1: true },
  designated_class2: { en: "Class 2 medicine", ja: "第2類医薬品", isClass1: false },
  class2: { en: "Class 2 medicine", ja: "第2類医薬品", isClass1: false },
  class3: { en: "Class 3 medicine", ja: "第3類医薬品", isClass1: false },
};
```

`getOtcClassInfo(otcClass)` がこのマップを返すだけの関数（`lib/otcClass.ts:17-19`）。

**重要**: この `getOtcClassInfo` を実際に import して使っているのは `app/find/FindResults.tsx:6,79,102-104` の1箇所のみ（v1ページ）。v2の4ページ（`/`, `/category/[slug]`, `/products/[slug]`, `/consult`）はこの関数を使っておらず、`otc_class === "class1"` の真偽だけを見て、`"第1類"` という文字列と `"Pharmacist required"` という文字列をJSX内に直接ハードコードしている（例: `app/category/[slug]/page.tsx:55-56`、`app/products/[slug]/page.tsx:59`）。designated_class2 / class2 の表示統合ロジックもv2側では使われていない（v2はclass1以外を一切区分表示しない設計のため）。

### foreign_brands の「Same as X」を出す判定がどこに書かれているか

共通関数化はされておらず、以下2箇所にほぼ同一のロジックが個別に書かれている。

- `app/category/[slug]/page.tsx:42-45`
```ts
const sameAs =
  product.ingredientSlugs.length === 1
    ? foreignBrands.find((brand) => brand.ingredient_slug === product.ingredientSlugs[0])
    : undefined;
```
- `app/products/[slug]/page.tsx:31-34`（同一パターン、`ingredientSlugs` の代わりに `ingredients` 配列の `.slug` を参照）

条件は共通で「有効成分がちょうど1つ、かつその成分slugが `foreign_brands.ingredient_slug` のいずれかと一致」。2つ以上成分がある商品は無条件で `undefined`（＝ラベルなし）になる。この制約は `CLAUDE.md:80-82` に文書化されている。

`app/find/FindResults.tsx` にも別ロジックがある（`:44-46`）が、こちらは「1つでも成分が一致すれば表示」で、単一成分限定の制約は付いていない（v1のまま、意図的に別ロジック）。

### 商品の並び順（sort_order）を適用している箇所

- `app/category/[slug]/page.tsx` は `getProductsByCategory()`（`lib/data.ts:97`）内の Supabase クエリで `.order("sort_order", { ascending: true })` を実行。**アプリ側で再ソートはしていない**（DBの返す順をそのまま `.map()` している）
- `app/products/[slug]/page.tsx` は商品自体の並び順は関係しない（1商品の詳細ページのため）。ただし成分表示は `getProductsSearchIndex()`（`lib/data.ts:75`）内で `.order("sort_order", { foreignTable: "product_ingredients", ascending: true })` を使い、`product_ingredients.sort_order`（箱の印刷順）で成分を並べている

products.sort_order は Supabase 上に実在する列（後述「6. 環境」参照）。ローカルの `supabase/schema.sql` にはこの列の定義が**存在しない**（stale）。

### .v2 クラスの置き場所

CSS Modules は使われていない。すべて `app/globals.css` 1ファイル（977行）に集約されており、`app/layout.tsx:2` で `import "./globals.css";` されている。

### 実際のクラス命名の例（5つ）

`app/globals.css` から実例を挙げる:

1. `.v2 .sign` — Home のカテゴリ行（案内標識ふう）。子要素に `.code`（符号）, `.tx`, `.en`, `.ja`, `.ar`（矢印）
2. `.v2 .pcard` — カテゴリ一覧の商品カード。子要素に `.ro`（ローマ字・主役）, `.nm`（日本語名・従）, `.meta`, `.req`
3. `.v2 .placard` — 商品詳細と完成カードで共用する「札」。子要素に `.ph`（黒帯）, `.pb`, `.big`, `.ro2`, `.en2`
4. `.v2 .kbox` / `.kbox.k1` — 箱の区分表示を模した枠（第1類のみ使用）
5. `.v2 .jacard .req` / `.v2 .jacard .cl` — 完成カード内の「依頼文」「結びの文」

### v1のスタイルとの共存がどう成立しているか

`:root` ブロックが**2つ**存在する（`app/globals.css:1` と `:509`）。1つ目がv1トークン（`--paper`, `--card`, `--ink`, `--ink-2`, `--ink-3`, `--rule`, `--rule-2`, `--seal`, `--seal-bg`, `--caution`, `--caution-bg`, `--caution-rule`, `--sans`, `--jp`, `--mono`）、2つ目がv2トークン（`--v2-bg`, `--v2-card`, `--v2-border`, `--v2-accent`, `--v2-accent-soft`, `--v2-ink`, `--v2-ink-2`, `--v2-ink-3`, `--v2-stop`, `--v2-stop-soft`, `--v2-font`）で、変数名を `--v2-` プレフィックスで分離しているため衝突しない。

クラス名については、v2固有の新規クラスはすべて `.v2 .xxx`（子孫セレクタ）としてスコープされている。v1ページ（`/about`, `/find`, `/phrases`, `/review`）は `<main className="page">` などv1クラスをそのまま使い続けており、`.v2` を親に持たないため v2 のスコープ付きルールの影響を受けない。

ただし完全に独立しているわけではなく、**同一葉クラス名がv1とv2の双方に存在するケースが複数回発生し、その都度パッチしている**（コミット履歴・会話履歴で確認済み）:

- `.tag` — v1の裸クラス（`app/globals.css` 内、`/find` が使用）と `.v2 .pcard .tag` が同名。`.v2 .pcard .tag` 側で `font-family` / `text-transform` / `letter-spacing` などv1側にしかない宣言を明示的に上書きして対処
- `.field` — v1の裸クラス（旧HomeSearch用）と `.v2 .field` が同名。同様に `display` / `border` / `padding` を明示リセット
- `.ask` — v1の裸クラス（旧Home見出し用、現在未使用）と衝突する可能性があったため、v2側は `.request` → 現在は `.req` にリネームして命名自体を回避
- `.jacard .note` → 同様の理由で `.cl` にリネーム

つまり「v1とv2は名前空間で分離」ではなく、**「.v2 という子孫セレクタでスコープしつつ、葉クラス名が衝突した場合は個別にプロパティを上書きするかリネームする」**という運用で共存している。body要素の背景・フォント指定（`app/globals.css:25-30`）はv1のまま変更されておらず、`.v2` 自身が `background` / `font-family` / `min-height: 100vh` を独自に持つことでv1のbody指定を実質的に覆っている（`app/globals.css:524-532`）。

### /review の実装（差分判定の条件と表示項目）

`app/review/page.tsx` に実装。認証なし、公開導線からのリンクなし（`CLAUDE.md:54` に明記の運用方針）。

**差分判定条件**（`app/review/page.tsx:48-51` の `needsReview()` 関数）:

```ts
function needsReview(product: ReviewProductRow) {
  if (!product.reviewed_at) return true;
  return new Date(product.updated_at).getTime() > new Date(product.reviewed_at).getTime();
}
```

つまり「`reviewed_at` が null」または「`updated_at` が `reviewed_at` より新しい」のいずれかで「未確認」タグ（`.tag-unreviewed`、文言は日本語で「未確認」）を表示する。
